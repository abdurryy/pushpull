# Keeping your Presenter simple

See also [React MVP anti-patterns](https://docs.google.com/presentation/d/1nb_akbKl7dp1cWFKl8ue3QYRkw4_t8zYU-9IX7njurw/edit#slide=id.g32dcfd403a6_0_34) (slides) and lecture 5 recording.

There is a tendency to do too much in the presenter, especially in the custom event handlers. A few principles

- **data** (state) generally belongs in Application State (model). **As different from what many videos and tutorials suggest, there are very few use cases for component state**, if you don't want to make your component universal and downloadable by the whole internet
- **data processing** belongs in Application State. We sometimes see in projects data kept in AS but its processing still done in the Presenter. When in a custom event handler you invoke more than a single Application State operation (POJO method, dispatching one Redux/Pinia/Mobx action/one action creator, setting one Recoil selector), it may be a sign that you need one more method/action/action creator/selector.
- many of the issues below occur in Presenter **custom event handlers** probably because *that's when you find out* about changes desired by the user. However, that does not mean the Presenter custom event handler should perform all the changes!
  - the Presenter custom event handler can simply change one primary item in the Application State and the rest (including persistence!) can be done using [Application State side effects](https://canvas.kth.se/courses/65821/pages/side-effects-with-reactive-objects-tw2-dot-2-tw3-dot-1). The side effect helps Application State find out about the change, so the side effect work can do its work without the Presenter being involved.
  - [a username/password authentication presenter](https://canvas.kth.se/courses/65821/pages/authentication-and-per-user-persistence-firebase) does not need to do more than request signup/signin in the authentication (e.g. firebase). The moment that is done, the rest of the system can find out via `onAuthStateChanged(ACB)` and perform further work without the presenter having to be involved

Redux note: simple presenters can be easily generated using react-redux connect or similar.

Here are a few ways to unnecessarily complicate your Presenter.

| **Coding issue in Presenter** | **Intuitive (but not correct) rationale** | **Solution** | **Grade penalty** | **Lab example solution** |
|---|---|---|---|---|
| **Persistence** in custom event handler | I've just found out that the user wants to change Application State property X, let's persist it!!! | Just change X in application state through a POJO method, Redux/Pinia/Mobx action, Recoil selector. Let an **application state side effect** (see [added hints for Redux, Recoil](https://canvas.kth.se/courses/65821/pages/side-effects-with-reactive-objects-tw2-dot-2-tw3-dot-1)) take care of persistence like we did in the lab! | **Yes**, Presenters should know nothing about persistence. Ideally not even the application state should know that it is persisted. That allows you to easily change your persistence layer | connectToFirebase presenters (and model) completely unaware of persistence |
| **Fetch** in custom event handler | I've just found out that the user is interested in the async resource X. Let's fetch it!!! | Just invoke an application state method/action creator/selector that does the fetch. The more code you isolate in Application State, the better. Furthermore, a method could simply set the parameters in application state, and the fetch could be performed in a side effect. | No but it is a bad "code smell" | doSearch() setCurrentDish() |
| change **component state** in custom event handler | The user just gave me the data X. I'll keep it in component state until I find Y and Z, then I plan to invoke application state with X, Y, Z as parameters | Keep X, Y, Z in Application State unless you want to write a universal component meant to be downloaded on the internet, independent of your application. Even if they are used by only one presenter, keeping them in application state can later on bring features like undo/redo etc.<br>This does not mean that component state is totally forbidden. Especially UI/graphics-related state like "the latest clicked pixel" makes sense to keep even in the View. | No, but you are writing UI-framework (React, Vue)-dependent code, when you could write framework-independent one | searchParams setSearchQuery() setSearchType() |
| **Multiple application state operations** in custom event handler | I just got news from the user so I'll ask Application State to perform X, then Y | Group X and Y in a single Application State operation (method, action creator, selector). They probably logically belong together! | Not directly but you are writing too much code in the UI (Presenter, UI-framework-dependent) when it belongs to Application State | setCurrentDish both sets the current dish and resolves a promise (though that could be a side effect) |
| **Mix use of application state and component state** in one Presenter | See component state | If you really need to use component state, see [slide](https://docs.google.com/presentation/d/17iHJd9XfHVlSultJQyzpGpaCZG4aWt32RTCdCMJ6kv4/edit#slide=id.g29b85862905_0_243)<br>make your Presenter/View independent of the application state and fire custom events. have another, application-state-aware Presenter that handles these custom events | See component state | none |
| **Mix application state and authenticatio**n in custom event handler | I've just learned that the user wants to sign up or sign in with these credentials. I'll tell that to my authentication layer (e.g. firebase authentication) **and** also set some application state while I'm at it | The username/password authentication presenter can be written isolated from the rest of the system. It only talks to the authentication service. If you want to change application state when a user logs in, use an authentication listener like `onAuthStateChanged(ACB)` | No, but it's a bad smell | none obligatory but see hints on the [per-user persistence](https://canvas.kth.se/courses/65821/pages/authentication-and-per-user-persistence-firebase) optional task |
| **Render UI/CSS** | I know that presenters should not render UI but I have this special case when I want to render HTML1, HTML2, or I want this DIV with some special CSS | Make a view that renders HTML1, HTML2, and just render a mini-presenter for that. Same for CSS, move that into your view. | **Yes.** Anything but a single DIV that simply puts sub-presenters of sub-views in sequence in presenters is regarded as a P-V mixup. In React you can even avoid the DIV by using <> ...</> Single suspense images are also OK (like in the lab) | Search presenter renders a single DIV to group two views |
| **Component state side effect** (e.g. react useEffect, Vue setup() watchEffect ) | Whenever X changes, I want my presenter to do Y | Once X is moved to Application State, the effect may actually belong to application state side effects! Do you really need an UI-framework-dependent effect? In other words, is the logic of your effect (app state) data-level, or UI-level? | No. But consider that UI framework side effects are heavily promoted because UI frameworks want to lock you in. Your effect will often belong in Application state. | none, but setCurrentDish could just set the ID, and let an App State side effect resolve the fetch |
| **Route used by presenter** (e.g. React useLocation, Vue useRoute) | I need my presenter to check the route to find a resource ID and set some View prop depending on that | The route is actually application-wide state, so often the application state needs to find out about your route change, especially if the route contains data like resource IDs. See [Keeping the parametric route in sync with Application State](https://canvas.kth.se/courses/65821/pages/navigation-routers-tw3-dot-3) | No. This is optional, but reflect on the routes that contain data, as being application state, and how it can be connected bi-directionally to application state. | none, but one use case is having the current dish ID and/or the search params **also** in the route. The presenter can still read them from application state |
